## §1 · Two engines

| | **194R — Incentive** | **194C — Visibility service** |
|---|---|---|
| Covers | every on-platform non-visibility payout + point redemptions + off-platform gifts/payouts | visibility payouts only |
| Deductor | the **CLIENT** | **GIFSY** |
| Aggregation level | per **PAN**, **within a tenant**, per FY | per **PAN**, **across the whole platform**, per FY |
| Threshold | cumulative **> ₹20,000 / FY** | **single > ₹30,000** OR **cumulative > ₹1,00,000 / FY** |
| Rate (PAN) | **10%** | **1%** individual/HUF · **2%** firm/company/LLP |
| Rate (no PAN) | **20%** | **20%** |
| Base | amount given | invoice **base, GST-EXCLUSIVE** |
| Special | — | compute **two columns**: (a) with thresholds, (b) no-threshold (TDS on every payment) |
| Who deposits | client (off-platform); platform tracks | Gifsy (off-platform); platform tracks |

## §2 · Aggregation — PAN-centric, FY-scoped

**PAN is a first-class key.** A TDS row may be `(PAN, amount, date)` with **no linked outlet/partner** —
off-platform uploads can carry PANs that were **never enrolled or KYC'd**, and those still get aggregated +
calculated.

**PAN + entity-type sources:** on-platform = `ChannelPartner.panNumber` + `entityType` (from KYC, P3); the
194C rate (1% vs 2%) keys off `entityType` (INDIVIDUAL/HUF → 1%, else 2%). Off-platform = PAN supplied in the
upload (entity type unknown → treat as "others"/2% for 194C unless provided; flag).

**194R taxable events (no double-count):**
1. **Cash payouts** (non-visibility credit payout entries) — counted **at disbursement = when marked PAID via
   the UTR upload** (transaction successful).
2. **Point redemptions** — counted **at fulfilment/disbursement** (voucher/gift/cash actually delivered),
   NOT at points-earned. (So a points award later redeemed is counted once, at redemption.)
3. **Off-platform 194R uploads** — see §5.
> Never count points at the moment they're *credited* — only when redeemed. Cash payouts and redemptions are
> distinct events, so no overlap.

**194C taxable event:** each visibility settlement amount (pre-GST base) to a PAN, platform-wide.

## §3 · Calculation — grossed-up (payer-borne), rounded to nearest rupee

The partner **receives the full amount**; the payer bears TDS **on top**:
**TDS = amount × rate / (1 − rate)**, rounded to the nearest whole rupee. e.g.
- 194R PAN: `amount × 10/90`; no-PAN: `amount × 20/80`.
- 194C 1%: `× 1/99`; 2%: `× 2/98`; no-PAN: `× 20/80`.

Single isolated helper (`tds.ts`) so the formula/rates live in exactly one audited place (mirrors the `money.ts`
pattern). All money in integer paise; TDS rounded to the rupee then stored as paise.

---

## §4 · Thresholds + the retroactive jump

- **Below threshold** → liability = 0 (nothing accrues yet).
- **On crossing** → liability applies to the **ENTIRE cumulative amount** for that PAN that FY (retroactive),
  then to every payment after. (Your ₹15k→₹20k example: at ₹15k = 0; the moment it crosses ₹20k, TDS becomes
  due on the whole accumulated amount.)
- **194C "no-threshold" column** ignores the threshold entirely — TDS on every payment from rupee one — so
  Gifsy can choose to over-deposit monthly and avoid a later un-recoverable shortfall.

## §5 · Off-platform 194R upload

Additive Excel upload — columns **date · PAN · outlet ID · amount** (the only relevant ones). Each upload
appends; multiple uploads accumulate into the PAN's FY total. Uploadable by client or Gifsy. PAN/outlet may be
**outside** the enrolled list — still aggregated + TDS-calculated.

## §6 · Outputs

1. **194R reference Excel (download)** — per tenant, per FY/period — **columns mirroring the TDS-return template**
   (deductee PAN, name, section 194R, amount paid, rate, TDS, date, …). The client uses it to file. *(Exact
   column list = open item §9.)*
2. **194C report** — per PAN, platform-level — **both columns** (with-threshold TDS, no-threshold TDS), so Gifsy
   decides what to deposit.
3. **Deposit-reconciliation upload** — the depositing party records TDS actually deposited to the government:
   **194R by the client, 194C by Gifsy**. **Simple additive columns: date · outlet ID · PAN · amount**
   (same shape as the off-platform upload; multiple uploads accumulate). The liability tracker nets these
   against the computed liability per PAN/FY.

## §7 · Liability tracker

Running **per PAN, per section, per FY**: **liability (computed) − deposited (uploaded) = outstanding.**
Surfaces the retroactive jump on threshold-crossing and the month-by-month outstanding balance, so by FY-end you
can see everything is deposited.
